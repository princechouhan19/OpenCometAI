# v1.15.4: field report round two

A second field round on the user's seven-section perception test page (18068 ms
total, "Faces detected: 0", 10 DOM sensitive fields, 5 text PII) showed the
small profile photo still escaping, and the screenshots exposed three more leak
classes. Four targeted fixes followed; nothing else changed.

## 1. Avatar guard

The v1.15.3 sweep only redacts model-confirmed faces, so a portrait the
detector refuses still shipped visible, as did an avatar painted as a CSS
`background-image`, which the v1.15.3 collector never saw. Both had been
reported three times.

`pageContextScan` now also collects background-image avatar elements: a word
prefilter on class, id and style for avatar hints, then a computed-style check,
tagged `hint: bg-avatar-hint`.

`privacy-filter.js` adds a guard in step 3b'': an image the page itself names as
an avatar or profile photo (24 to 180 CSS px) that no confirmed face covers is
redacted on its element rect without model confirmation, with
`source: dom-avatar-guard` and confidence 0.5. The stand-down test is a confirmed
face box centred inside the element, because measured coverage ratios span 33%
to 52% and ratio thresholds mis-fire.

The asymmetry is deliberate. A wrongly blurred hinted image costs a black
square; a missed face ships identity. Un-hinted icons and logos remain scanned
and never redacted.

## 2. Person-name fields

A "Full name" label above `<input value="Aarav Sharma">` carried no attribute
signal at all. Both scanners now read the field's visible label (`el.labels`, a
wrapping label, a label inside the same container, or a previous-sibling label)
and match a word-bounded person-name family: full, first, last, given, family,
surname; customer, card-name, card-holder, account-holder; father's, mother's,
spouse, nominee; billing, shipping and contact name; and
`autocomplete="name|given-name|…"`.

"filename" and "hostname" cannot match because of the word boundary, and the
"Search public information" box stays untouched as a negative control.

## 3. Pixel-only PII through targeted OCR crops

The full-page OCR pass read only one value of the canvas line, the phone, and
neither of the two pixel-only contact cards. Small text on busy pages is where
Tesseract's page segmentation drops lines.

`pageContextScan` now returns `pixelTextRects`: visible canvases of 60 px or
more, sorted by area, capped at 12. The OCR pass re-reads each region as an
isolated ×2 upscaled crop, decoding once and reusing the warmed worker, then
runs both the shared PII detector (space-joined and line-fused) and a structural
battery mirroring the DOM text rules: email, 4-4-4 Aadhaar shape, PAN, API key,
13 to 19 digit cards, and phones of 10 digits or more with plausibility guards,
longest span winning.

Findings map back through the crop's word spans to full-image boxes. Raw crop
text never propagates. `detectPiiInText` semantics are untouched, and the
41-test corpus still locks its precision.

## 4. DOM text walker budget, 140 to 400

The battery walker decrements on every accepted text node, so on the
seven-section page it ran out around section 3. The "Invoice email:
billing.pixel@example.com" row in section 4 was never scanned and shipped
readable. A budget of 400 stays in milliseconds and remains bounded.
