# v1.19.0: disambiguation, daemon counter, Hindi (2026-09-16)

Repeated tags, meaning the same control rendered several times with the same
visible label, now get disambiguation receipts that resolve to the exact
control. The authorization daemon gains a visible counter. Purchase and deletion
intent and tags are matched in Hindi with both negation orders, tested by a set
whose structure mirrors the English one.

## Disambiguation

A score-based resolver silently picks the first tie when four "Buy Now" buttons
score equally. This release removes the ambiguity at both ends.

**Inventory side** (`sw.js` page scan). Every member of a repeated
(tag, visible label) group of two or more now carries:

- `dup: "2 of 4"`, its ordinal position in the group;
- `pos: "top-left"`, the viewport zone of that control, from its centre across
  top, middle or bottom and left, centre or right;
- `nearform: "iPhone 15 case"`, the nearest form or section label, resolved from
  form name, fieldset legend, ancestor aria-label or ancestor heading, capped at
  40 characters;
- `ref: "Buy Now #2"`, the canonical resolvable name.

Single controls stay untouched, so unambiguous elements get no tag noise.

**Resolver side** (`actions.js` `domClick`). The selector `"Buy Now #2"` parses
as an ordinal and clicks the second equal-labelled control with
`resolution: 'ordinal'`. An out-of-range ordinal fails with the group size, as
in `"Buy Now" matched 4 controls — use #1…#4`. An ordinal that matches no group
falls through to the standard chain on the base text.

**Receipts.** Every click result carries the same receipt
(`disambiguation: { dup, pos, nearform, ref }`), so history shows which
duplicate fired. The click's interactive context also passes `ref` and `dup`
through as an exact-control fallback.

The pure primitives live in `src/lib/element-disambiguate.js` and are
node-testable. The in-page implementations are compact self-contained mirrors,
because serialized page functions cannot import.

## Daemon counter

Every `authorizeAction` verdict is tallied per run and for the extension's
lifetime.

- **Per run** (`agentState.guardianCounter`, both loops): `checks`, `risky`,
  `authorized`, `blocked`, `exits`, `faults`.
- **Lifetime** (`storage.local` key `opencometGuardianLifetime`): flushed once
  per run at every terminal path, whether done, stopped, max steps, guardian
  exit, error or user stop. The flush consumes the per-run counter, so a run is
  never counted twice. A crash loses only that run's in-memory remainder.
- **Surfaced**: `AGENT_DONE` broadcasts carry
  `data.guardian = { summary, checks, risky, authorized, blocked, exits, faults }`
  when the gate saw activity, for example `checks 14 · risky 3 (authorized 1) ·
  blocked 2 · exits 1 · faults 0`.

## Hindi

The risk taxonomy and authorization phrases cover Devanagari end to end:
element triggers including खरीदें, कार्ट में डालें, चेकआउट, भुगतान, ऑर्डर करें,
डिलीट, हटाओ, मिटाओ and रद्द करें; authorization phrases with benign-context
suppressions; and both negation orders.

- **Pre-verbal**, as in "कुछ भी मत खरीदो", where the negator precedes the verb.
- **Post-verbal**, as in "खरीदो मत" or "खरीदना ज़रूरी नहीं", caught by a
  Devanagari-only 16-character after-window that cannot fire on English prose,
  so no English regression is possible.

JavaScript word boundaries are ASCII-only and never match around Devanagari
letters, so the Hindi patterns use substring and variant matching with explicit
suffix forms.

`scripts/test_v1190_disambiguation.mjs` runs an English set and a Hindi set with
the same structure: mirrored cases, same assertions, same verdict-shape parity
per pair.
