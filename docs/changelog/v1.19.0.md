# v1.19.0 — Disambiguation + Daemon Counter + Hindi (2026-09-16)

Repeated tags (the same control rendered several times with the same visible
label — "Buy Now" ×4) now receive **disambiguation receipts** — DOM/hint
context plus ordinal positioning — that **resolve to the exact control**. The
Task Authorization Daemon gains a **visible counter**. And purchase/deletion
intent + tags are matched in **Hindi (Devanagari)**, with **both negative word
orders**, tested by a set whose shape is byte-for-byte the same as the English
one.

## Disambiguation: repeated tags → exact controls

A score-based resolver silently picks the FIRST tie when four "Buy Now"
buttons tie at the same score. v1.19.0 removes the ambiguity at both ends:

- **Inventory side** (`sw.js` page scan): every member of a repeated
  (tag, visible-label) group of ≥2 now carries
  - `dup: "2 of 4"` — its ordinal position inside the group,
  - `pos: "top-left"` — the viewport zone of that specific control
    (top/middle/bottom × left/center/right, from the element center),
  - `nearform: "iPhone 15 case"` — the nearest form/section context label
    (form name → fieldset legend → ancestor aria-label → ancestor heading,
    capped at 40 chars),
  - `ref: "Buy Now #2"` — the canonical resolvable name.
  Singles stay untouched: no tag noise for unambiguous controls.
- **Resolver side** (`actions.js` domClick): the selector `"Buy Now #2"`
  parses as an ordinal and clicks the 2nd equal-labeled control
  (`resolution: 'ordinal'`). Out-of-range ordinals fail **honestly** with the
  group size (`"Buy Now" matched 4 controls — use #1…#4`), and an ordinal that
  matches no group falls through to the standard chain on the base text.
- **Receipt side**: every click result carries back the same receipt
  (`disambiguation: { dup, pos, nearform, ref }`), so history proves WHICH
  duplicate fired. The click's interactive context also passes `ref`/`dup`
  through as an exact-control fallback.

The pure primitives live in `src/lib/element-disambiguate.js`
(node-testable); the in-page implementations are compact self-contained
mirrors (serialized page functions cannot import).

## Daemon Counter

Every `authorizeAction` verdict is now tallied — per run and for the
extension's lifetime:

- **Per-run** (`agentState.guardianCounter`, both loops): `checks`, `risky`,
  `authorized`, `blocked`, `exits`, `faults`.
- **Lifetime** (`storage.local 'opencometGuardianLifetime'`): flushed exactly
  once per run at every honest terminal path (done / stopped / max-steps /
  guardian exit / error / user stop). The flush consumes the per-run counter,
  so a run can never be counted twice; a crash loses only the in-memory
  remainder of that run's accounting — stated honestly, not hidden.
- **Surfaced**: `AGENT_DONE` broadcasts carry
  `data.guardian = { summary, checks, risky, authorized, blocked, exits,
  faults }` when the gate saw any activity — e.g. `checks 14 · risky 3
  (authorized 1) · blocked 2 · exits 1 · faults 0`.

## Hindi: intent + tags, both negation orders

The guardian's risk taxonomy and authorization phrases cover Hindi
(Devanagari) end-to-end — element triggers (खरीदें / कार्ट में डालें / चेकआउट /
भुगतान / ऑर्डर करें / डिलीट / हटाओ / मिटाओ / रद्द करें …), authorization
phrases with benign-context suppressions (ऑर्डर स्टेटस, भुगतान हिस्ट्री,
प्रदान-lookalike guard), and **both negative word orders**:

- **Pre-verbal**: "कुछ भी **मत खरीदो**" — the negator precedes the verb;
- **Post-verbal**: "**खरीदो मत**" / "खरीदना ज़रूरी नहीं" — the negator follows
  the verb, caught by a Devanagari-only 16-char after-window that can never
  fire on English prose (so no English regression is possible).

JS `\b` is ASCII-only and never matches around Devanagari letters, so Hindi
patterns deliberately use substring/variant matching with explicit suffix
forms. The test harness (`scripts/test_v1190_disambiguation.mjs`) runs an
English set and a Hindi set with the **same structure** — mirrored cases,
same assertions, same verdict-shape parity per pair.
