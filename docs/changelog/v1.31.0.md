## 1. Statistical rigor — published latency numbers now carry error bars

v1.30.0 measured every case; the *claims* were still point estimates. v1.31.0 adds the statistics layer on top of those 815 samples:

- **`bootstrapCi()` in `OpenCometBench/latency.js`** — deterministic percentile bootstrap confidence interval for any quantile (seeded mulberry32 PRNG: same samples → same interval, run after run; empty input stays `n=0` — a missing measurement is never fabricated, same policy as `latencyStats`).
- **`mannWhitneyU()` in `OpenCometBench/latency.js`** — nonparametric rank-sum test (normal approximation with tie correction) for A/B latency comparisons.
- **`run-all.js` attaches + prints CIs** — every suite's `metrics.latency` now carries `ciP50`/`ciP95` (95%, 1000 resamples) and the table prints `p50=0.016ms [CI95 0.014–0.017] · p95=0.105ms [CI95 0.057–0.165]` style lines. Claims with overlapping CIs can be recognised as such instead of being over-read.

## 2. Regression gate — "quality byte-identical" is now ENFORCED, not narrated

- **`OpenCometBench/regression-gate.mjs`** compares a current `run-all.js --json` against a committed baseline (`OpenCometBench/baselines/v1.30.0-unit.json`):
  1. **Any quality-metric change** (P/R/F1, coverage/IoU, accuracy, leak counts — latency fields excluded from the comparison) is a **hard block**;
  2. a suite's p95 may grow ≤25% **and** only blocks when the per-case sample distributions actually shifted (Mann-Whitney U, p < 0.01, two-sided) — machine noise no longer blocks releases, and real slowdowns no longer hide behind it.
- **GitHub Actions** (`.github/workflows/bench-gate.yml`) runs the 6 offline unit suites + the gate on every push/PR to `main`; results uploaded as an artifact. No dependencies, no browser tier in CI (the Node tier is deterministic).
- **Measured on this very release**: the fuzz suite's p95 grew **+40.4%** vs the baseline on this machine — **over** the 25% budget — but MWU says **p = 0.103**: machine noise, gate allows it. A naive threshold gate would have false-blocked the release; a naive "ignore latency" gate would have hidden a real one.

## 3. OpenRouter prompt-cache stickiness — the provider keeps the prefix warm

The decision prompt was already cache-shaped (byte-stable `SYSTEM_PROMPT`, KV-cache-friendly block ordering documented in `privacy-agent.js`). v1.31.0 completes the loop on the wire, host-gated to `openrouter.ai` (generic OpenAI-compatible gateways see **zero** behavior change):

- **`session_id` body field** — deterministic per-task FNV-1a hash (`sessionIdForTask`, `oc-<base36>`; no task text, URL, or PII leaves the device). OpenRouter's provider sticky routing uses it to pin every step of a run to the same cache-warm endpoint from the FIRST turn.
- **`cache_control` breakpoint on the system message** — the static policy prefix becomes explicitly cacheable; OpenRouter translates the Anthropic-style marker per provider. A strict provider that rejects the shape gets **one automatic clean retry** of the full ladder without the breakpoint.
- **Cache telemetry** — `cached_tokens` / cache-write / discount are normalised (`cacheUsageFrom`), logged (`💰 … prompt cache: Ntok read`), and surfaced through the `onUsage` payload — so the first real OpenRouter run produces measured hit-rate numbers for the README without any extra tooling.

## 4. ORT-Web thread unlock — shipped as a capability, measured HONESTLY for yolos-tiny

- The vendored wasm was always the **threaded** build (`ort-wasm-simd-threaded.asyncify.wasm`, 23.6 MB) but `numThreads` was pinned to 1 on a stale "no crossOriginIsolated in extension pages" assumption. `ortThreadCount()` now **feature-detects** (SharedArrayBuffer present AND page not un-isolated → up to 4 threads, capped by `hardwareConcurrency`; otherwise exactly 1 — byte-identical to v1.30.0). The chosen count is exposed via `getLocalVisionStats().threads`.
- **Measured (this release, sandbox CI, 2 cores): NEUTRAL for yolos-tiny.** `OpenCometBench/probe-ort-threads.mjs` runs the real vendored stack + real model in a COOP/COEP-isolated page:
  - threads=1 median **9850 ms** vs threads=2 **10106 ms** (0.97×) and threads=4 **9626 ms** (1.01×) — within run-to-run noise;
  - **box parity IDENTICAL** across all thread counts (quality untouched, again);
  - consistent with the model resizing internally to a fixed 224px resolution (v1.16.0 downscale probe: IoU 1.000, latency ratio 0.99) — YOLOS compute is fixed-size and not threading-friendly at this scale. Upstream reports also show WebGPU is currently *slower* than wasm for YOLOS-family models.
- **Conclusion recorded for the next planner:** the honest levers for the ~7–10 s changed-frame YOLO leg are (a) the memo + warm-up (shipped) and (b) a **detector model swap** (e.g. YOLO26n, NMS-free, 38.9 ms CPU ONNX @ 640 on desktop-class cores) — which first requires recalibrating the quality gate on its outputs. The thread unlock stays: it is free, safe, and benefits the ViT/NER pipelines and any future larger graph.

## 5. Adversarial e2e — full runs no longer OOM, and every case now has a TTFA

- **Memory guard:** the runner previously kept ONE persistent Chromium context (extension + offscreen ML document + models + per-case pages) alive across all 23 cases — it OOM-crashed around case 16 in long runs, so full-run evidence had to be assembled from isolated re-runs. `--context-budget=N` (default 8) rotates to a fresh context — extension profile, SW, settings/OCR toggles and helper page rebuilt automatically — so a **full 23/23 run now completes in one invocation**.
- **TTFA (time-to-first-decision):** every case row carries `ttfaMs` — task start → first recorded `/agent/decide` arrival (capture + perception + sanitize + gates + wire). Post-rotation cold starts show up honestly in the numbers (first case after a rotation pays the extension warm-up) instead of being averaged away.
- The report `meta` now records `contextBudget` + `contextRotations`, making the execution shape auditable from the evidence file alone.
